# AUDIT: current implementation vs `hangwin/mcp-chrome`

Date: 2026-08-08
Reviewed commit of `mcp-chrome`: `f48e717` (2026-01-06), MIT licensed, © 2024 hangye.
Current implementation: 5,386 lines of TypeScript across `src/` (Playwright-based, written from scratch in this repo, never released, no tests).

The comparison was done by cloning the repo and reading the source, not from documentation.

---

## The finding that decides the architecture

**Chrome 136+ refuses to honour `--remote-debugging-port` or `--remote-debugging-pipe` when the browser is using its default user-data directory.** The switches must be paired with a `--user-data-dir` pointing somewhere non-standard, because a non-default directory gets a different encryption key and therefore cannot decrypt the real profile's cookies and passwords. This was a deliberate hardening step against infostealer malware.

Sources: [Chrome for Developers — Changes to remote debugging switches to improve security](https://developer.chrome.com/blog/remote-debugging-port), [Chrome 136 update breaks remote debugging functionality](https://community.latenode.com/t/chrome-136-update-breaks-remote-debugging-functionality/21829)

The consequence for this product is direct and unavoidable:

> Playwright, in any of its modes, cannot drive the user's real, already-authenticated Chrome or Edge profile.

`connectOverCDP` needs remote debugging on the real profile, which is now blocked. `launchPersistentContext` works, but only against a **separate** profile directory, which means the user logs into every site again inside a browser that is not the one they use. That is precisely the problem the product exists to remove ("log into a website normally, including SSO or 2FA").

The current implementation is built on `launchPersistentContext`. It is well-formed, but it solves a different problem than the one stated. A Chrome/Edge extension talking to a local native-messaging host is currently the only supported way to automate the user's actual logged-in profile. `mcp-chrome` already implements that bridge and it works.

**This invalidates the browser-attachment layer of the current code (`launcher.ts`, `session.ts`, `detect.ts`, and the Playwright half of `runner.ts` — roughly 990 lines) as a production execution engine.** Everything above that layer largely survives.

---

## The second finding: what we are actually competing on

`mcp-chrome` publishes **27 always-on tools** whose JSON schemas total roughly **45 KB, about 11,000 tokens**, measured from `packages/shared/src/tools.ts`. That cost is paid by every agent, in every session, before any work happens. Its dynamic flow tools (`flow.<slug>`) are added on top of that baseline, not instead of it.

That is the number our adapter model has to beat. A site adapter exposing `linkedin_search_people` plus four siblings should cost a few hundred tokens and one tool call, against ~11k tokens of preamble and an eight-call snapshot/click/snapshot loop. The benchmark in the plan should measure exactly this, and the baseline is already established.

The current implementation anticipated this: `genericTools: 'auto'` exposes ad-hoc browse tools **only while a site has no recipes**, so the tool list shrinks as the site gets properly modelled. That policy is worth keeping.

## Smaller findings worth recording

**Dotted tool names are a compatibility risk.** `mcp-chrome` publishes `flow.<slug>`, and the plan document specifies `adapter.id.toolName`. Hosts commonly constrain tool names to `^[a-zA-Z0-9_-]{1,64}$` after prefixing (Claude Code exposes MCP tools as `mcp__<server>__<tool>`), and a dot fails that pattern. `linkedin_search_people` reads the same and is portable. Where a true dotted namespace is wanted, run one MCP server per site so the host supplies the namespace: `mcp__linkedin__search_people`. The current implementation already does both (`ygs serve --site linkedin` drops the prefix).

**`chrome_read_page` before every locate.** `handlers/click.ts:52` calls `READ_PAGE` before locating, to populate element refs. On a large page this is the dominant cost of a click and part of why generic browsing is expensive. Adapters that navigate straight to a known URL and extract by selector avoid it entirely.

**No Edge support in the native host registration.** `BrowserType` covers Chrome and Chromium only. Edge is a stated v1 target and needs its own manifest path and registry key.

**Out-of-scope surface is the majority of the extension.** Of ~152k lines outside `node_modules`, the visual web editor (`web-editor-v2/`, `web-editor/`), the ONNX runtime (`public/libs/ort.min.js`), `semantic-similarity-engine.ts`, `vector-database.ts` and the agent chat service (`native-server/src/agent/`, with Claude and Codex engines) are all unrelated to a browser bridge. Per your call: the vector database, embeddings and semantic tab search come out; the interaction surface (element picker, quick panel, side panel) stays in scope.

## What survives from the 5,386 lines already written

Kept roughly as-is: `pack.ts`, `commands/share.ts`, `mcp/naming.ts`, `browser/origins.ts`, `config/schema.ts` (step and param schemas), `config/store.ts`, `config/paths.ts`, `util/*`, and the CLI shape in `cli.ts` + `commands/`.

Kept as ideas, re-implemented against the new engine: `page-tools.ts` readable-text extraction, `genericTools: 'auto'` policy, list-extraction with auto-derived fields, password-to-secret-parameter handling, and the compact result formatting.

Dropped: `browser/launcher.ts`, `browser/detect.ts`, `browser/session.ts`, `browser/selectors.ts`, and the Playwright execution path in `browser/runner.ts`. Playwright stays in the repo for adapter development, integration tests and locator semantics, as the plan allows — it is no longer the production engine.

`recorder/overlay.js` and `recorder/verify.ts` are superseded by the upstream recorder, minus the two behaviours called out above, which we graft on.
